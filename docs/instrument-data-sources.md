# Instrument data sources for mixed-sensor coverage

**Research snapshot:** 2026-10-23 UTC. This note compares public catalogues, official mission material, product APIs, and parsing tools that can support instrument discovery and geometry research. It is a source map, not a geometry approval for any named sensor.

## Recommendation

Use mission-owner technical documentation as authority for intrinsic sensor geometry. Use OSCAR/Space, CEOS MIM, NASA CMR/GCMD, and mission catalogues to discover names, platform variants, modes, and products. OSCAR has platform-level instrument records and a JSON API, but WMO says records reflect its best knowledge with agency support and carry no accuracy or completeness warranty. WMO permits redistribution with acknowledgment. Cite an applicable mission document before treating an OSCAR geometry value as verified. [OSCAR overview][oscar] [OSCAR API][oscar-api] [OSCAR disclaimer][oscar-disclaimer]

Keep three kinds of information separate:

1. **Designed capability:** field of view, scan or steering limits, swath, spectral response, and operating mode. Obtain these from the mission owner or an instrument-team specification.
2. **Catalogue identity and product metadata:** platform, instrument, mode, acquisition time, orbit, footprint, and assets. CMR, CDSE STAC, and ASF help identify actual acquisitions. A product footprint is not the sensor's full accessible region or tasking envelope. [STAC core][stac] [STAC view][stac-view] [CDSE STAC][cdse-stac]
3. **Computed coverage:** a model result derived from approved geometry and orbit assumptions. Do not equate a scene footprint, nominal swath, or center viewing angle with the field of regard.

Index by spacecraft, instrument variant, mode, and product where relevant. Preserve source names as aliases. Store each value with its unit, document revision, page or field, URL, retrieval date, and interpretation. If sources conflict or only give swath, leave geometry unresolved for review.

## Acquisition and parsing approach

1. **Resolve platform and instrument.** Search OSCAR and CEOS MIM by aliases, then check the operator's mission page. For NASA products, query CMR by controlled instrument name and retain the platform/instrument pair. GCMD UUIDs identify vocabulary terms; they do not prove similarly named instruments share geometry. [OSCAR API][oscar-api] [CEOS MIM][ceos-mim] [CMR Search API][cmr-api] [KMS][gcmd-kms]
2. **Cite each geometry field to a mission document.** Use official instrument guides, requirements, characterization documents, calibration papers, product specifications, and operations notices. Record variant, mode, scan/steering direction, and value definition. Check a PDF's issue date and applicability even when its landing page is current. [ESA mission documents][esa-docs] [USGS Landsat handbooks][usgs-handbooks]
3. **Parse catalogues as acquisition records.** In STAC, read geometry, time, collection, assets, platform, instruments, and only declared extension fields. Keep item and collection metadata separate. Pin CMR's UMM JSON version and parse by schema. For ASF, use its documented API and product files. [STAC][stac] [CMR API][cmr-api] [ASF API][asf-api]
4. **Keep provenance.** Store raw and normalized values, units, source URL and revision, source field/page, platform/instrument/mode, and rationale. Keep scan range, detector IFOV, scene-center angle, swath, and taskable FoR as separate fields. Preserve unknowns rather than borrowing values from a similar instrument.
5. **Parse documents conservatively.** Use schemas and versioned XML/MTL definitions where available. Treat HTML/PDF extraction as a review aid and retain page, heading, footnote, and units. Reject unknown units and ambiguous ranges. Snapshot changing records and follow provider terms when re-fetching. ASF documents its Search API limits; other providers' quotas, bulk licenses, and SLAs were not verified. An unauthenticated response alone proves none of those. [ASF API guidance][asf-rate]

## Source conflicts and known limits

Catalogues mix instrument names, processed product names, design values, current spacecraft configuration, and single-acquisition metadata. Keep those concepts separate. Use mission-owner specifications for designed capability, operator pages for current status, and product records for a specific acquisition. [CMR UMM][umm-common] [CMR Search API][cmr-api]

OSCAR and CEOS are cross-mission indexes, not substitutes for a current instrument-team specification. CMR and GCMD improve name matching but do not supply all geometry. A scene-center angle or product footprint cannot establish every feasible pointing direction. STAC standardizes fields when a provider populates them, but does not require full sensor geometry. Sentinel-2's current extension campaign also differs from older nominal schedules. [OSCAR disclaimer][oscar-disclaimer] [CMR API][cmr-api] [STAC SAT][stac-sat] [STAC View][stac-view] [SentiWiki][sentiwiki-s2]

Do not derive one geometry family from another. For example, the Sentinel-2 instrument uses push-broom imaging, while SAR product metadata describes beam and pointing direction; their footprints and pointing constraints differ. A nominal nadir swath cannot prove off-nadir access, and a product footprint cannot define the full pointing envelope. Each sensor needs an explicit support decision, and the model quantity must match the sourced value. [SentiWiki MSI description][sentiwiki-s2] [STAC SAR][stac-sar] [STAC View][stac-view]

## TAT-C geometry and compatibility

Source authority, successful number extraction, and compatibility with the coverage model are separate checks. The current resolver uses OSCAR's HTML capabilities search for name lookup, its JSON API for record identity and platform associations, and HTML instrument tables for specifications. `server.py` passes the specification dictionary to the geometry parser, but not OSCAR type or classification (`apps/mcp-server/src/oscar_client.py:1-28, 310-364`, `apps/mcp-server/src/server.py:516-521`). The geometry path then creates one TAT-C `Instrument` per satellite and uses one shared input angle or swath (`apps/mcp-server/src/generic_coverage.py:211-235, 237`).

The four source-checked sensors show why one extracted width cannot define a common geometry:

| Sensor | Reviewed evidence and modeling limit |
| --- | --- |
| AMSR2 on GCOM-W1 | JAXA distinguishes a nominal 1,450 km swath at scan angles of +/-61 degrees from a 1,620 km effective product width at +/-75 degrees. It also reports 55 degrees nominal incidence and frequency-specific beam properties. These scopes must remain separate. Ground incidence is not spacecraft off-nadir angle, and the current nadir-cone approximation is not a conical-scan model. [JAXA AMSR2 table][amsr2-current] |
| Sentinel-1 C-SAR | The mission table gives 250 km for IW and 400 km for EW, with separate incidence and spacecraft off-nadir ranges by subswath and altitude. Keep mode, subswath, look direction, near/far limits, angle reference, platform, and valid/operating dates with each record. A single nadir-centered strip misplaces side-looking SAR coverage. Mission capability tables do not establish a particular acquisition plan. [Sentinel-1 mission table][s1-mission] [Product definition, Issue 2.8][s1-product] |
| NISAR L-SAR | The snow prompt's 252 km value conflicts with NASA's 242 km satellite-page value. Preserve both with source and scope, and require a reviewed choice instead of silently replacing either. NASA describes NISAR as left-looking and assigns observation modes by region; retain band, mode, look direction, source date, and operational validity. Its observation-strategy page is dated 2025-07-23, so check for later mission changes before operational use. [NASA satellite page][nisar-satellite] [NASA observation strategy][nisar-strategy] |
| ICESat-2 ATLAS | NASA describes six beams in three pairs and an 11 m footprint. The beams form separate tracks; their roughly 6.6 km outer span is not a continuously observed strip. Treat that span only as an explicit approximation, not as the laser footprint or solid area coverage. Predicted tracks also carry timing and location limits, and ATL03 provides retrospective photon locations, heights, and times in HDF5. [ATLAS specifications][icesat-specs] [ATLAS data products][icesat-products] [NSIDC ATL03 v7][atl03] |

The parser probe loaded the unchanged `geometry.py` under Python 3.12 with only its unused `tatc.utils` import omitted. It used synthetic strings, not current OSCAR records, and ran no orbit calculation. The parser marked a conical 1,450 km example and six separated laser beams with a 6.6 km span as conclusive. It marked conflicting IW/EW widths ambiguous, but a side-looking warning in a separate field did not invalidate a swath candidate; nor did it compare a swath candidate with a separate field-of-regard candidate. These results show extraction and within-kind conflict handling only. A `conclusive` parser status does not show that TAT-C represents the geometry correctly or that coverage is scientifically valid. The synthetic cases and outputs are recorded in `.audit/parser-probe-results.json`.

The installed local package and PyPI release checked on 2026-10-23 are TAT-C 3.5.1. The repository requirement is `tatc>=3.5.1`, so installs are not pinned. Upstream `main` and documentation marked 3.6.0 include `ConicalInstrument` and newer pointing features, but `ConicalInstrument` is absent from the published 3.5.1 package. Treat the 3.6 material as upstream guidance, not an available runtime API; choose and verify a dependency version before relying on it. TAT-C's conical validation also warns that matching swath widths do not reproduce conical timing or footprints. [PyPI TAT-C release metadata][tatc-pypi] [Upstream ConicalInstrument][tatc-conical] [Conical AMSR2 validation][tatc-amsr2-validation] [SAR validation examples][tatc-sar-validation]

Use a small, versioned, maintainer-reviewed configuration registry as the runtime authority. Each record should identify platform, instrument, mode, band, geometry family, valid and operating dates, units, angle reference, source locator and revision, retrieval date, and status (`supported`, `approximate`, or `unsupported`). Registry provenance and maintainer review establish data readiness, not model validation. Mark a record `supported` only when its TAT-C version is pinned, its geometry mapping is tested, and mission/mode reference comparisons meet stated engineering tolerances within a stated applicability. This research ran no orbital validation and approves no named sensor mapping. Existing upstream validation examples are reference material, not proof that this MCP is correct. Keep provenance per field, preserve raw evidence, cache source snapshots, and use deterministic source adapters with pagination, schema checks, semantic checks, and explicit source-conflict handling. Chat should resolve approved records and surface unresolved conflicts; it should not scrape arbitrary numbers and silently treat them as compatible. Keep orbit providers and acquisition catalogs separate from instrument capability. Store instrument operating intervals separately from spacecraft orbit availability, and preserve per-instrument outputs before computing a combined interval union of geometric access so overlaps do not double count. The union reports geometric access only. Keep measurement-specific suitability and quality separate because microwave, SAR, and laser are not interchangeable snow measurements.
